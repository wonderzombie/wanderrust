# TILEIDX: FLIP

## SUMMARY

LDtk has the option to flip tiles randomly as part of its procedural generation feature set (see LDtk documentation). In addition to small ~1px offsets applied randomly, flipping tiles horizontally adds a bit of visual texture to a scene. When sprites are asymmetrical and offset here and there, it adds a more organic feel. 

LDtk encodes these transforms in its JSON format, so it is available. wanderrust just doesn't use it; wanderrust uses `TileIdx`, aka the index of the tile in the spreadsheet. `TileIdx` is sufficient for the wanderrust renderers to figure out what to do with a tile, and in general I would *strongly* prefer to avoid changing this API.

## OBJECTIVE

Apropos of flipping tiles, use LDtk's data format to flip tiles accordingly (almost always horizontally). This API is very simple and we want to preserve that.

## BACKGROUND

### REFRESHER ON `TileIdx` AND `Sprite`

**`TileIdx` is an enum** generated by a macro that wraps a `usize` which corresponds to a Bevy `TextureAtlas` `index`. The `TextureAtlas` lives on `Sprite`.

`Sprite` also has `flip_x` and `flip_y`.

`sync_tiles()` in `map.rs` *used* to sync only `MapTile`. Now it syncs anything with a `Changed<TileIdx>`, which selects addition/insertion.

### LDtk

*See also [https://ldtk.io/json/](). Documenting the entire format is out of scope.*

The key piece is in a layer instance of type `Tile`. The key field therein is `gridTiles`, which contains a list of dictionaries, and each dictionary represents a tile in the layer. These are documented in [Tile layer instances](https://ldtk.io/docs/game-dev/json-overview/layer-instances/#tile-layer-instances), and `f` is the one we want:

    f: “Flip bits”, a 2-bits integer to represent the mirror transformations of the tile. Bit 0 is X symmetry and bit 1 is Y symmetry. So you get the following possible values:
    f=0 : no transformation
    f=1 : horizontal (X) symmetry
    f=2 : vertical (Y) symmetry
    f=3 : both horizontal (X) and vertical (Y) symmetries

This is quite simple. We don't have anything like this in our TileIdx API.

*See also [TileMapLayer](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html#tilemaplayer), et al.*

Godot has a clever way of getting around this problem, but it won't work for us. Godot allows users not to have to create a separate tile for `flip_v`, `flip_h`, or `transpose` using bitwise OR on part of a tile's identifier. 

In wanderrust, `TileIdx` *is* the identifier.

### LOADING TILES

The provenance of any given `TileIdx` is from `ldtk_loader.rs`, via `LdtkGridTile`, which is a 1:1 mapping between the *relevant* fields:

```rust
#[derive(Debug, Deserialize, Default, Clone, Copy)]
pub struct LdtkGridTile {
    #[serde(rename = "t")]
    pub atlas_idx: usize,
    #[serde(rename = "px")]
    px: Vec2,
    #[serde(rename = "f")] // new
    f: i8,                 // new
}
```

The work of translating from `LdtkGridTile` to types used by wanderrust happens in the same file, in `get_grid_tiles()`. In `tilemap.rs`, we have this foundational type alias, used by the tilemap and ldtk_loader modules:

```rust
// tilemap.rs
pub type TileSpec = (TileIdx, Cell);
```

```rust
// ldtk_loader.rs
let tile_idx = TileIdx::from_idx(grid_tile.atlas_idx).unwrap_or(TileIdx::GridSquare);
let cell = grid_tile.into_cell(level_px_height, world_depth);
// ... omit validation, et al
new_tiles.push((tile_idx, cell)); // <-- the tuple is a TileSpec
```

## DESIGN

### DESERIALIZATION

In `tiles.rs`, we add this:

```rust
#[derive(Component, Default, Debug)]
pub struct TileXform {
    pub flip_x: bool,
    pub flip_y: bool,
}
```

In `tilemap.rs`, change `TileSpec`:

```rust
pub type TileSpec = (TileIdx, Cell, TileXform);
```

In `ldtk_loader.rs`, deserialize `f` by adding it to `LdtkGridTile` as `i8` and implement `From`:

```rust
impl From<LdtkGridTile> for TileXform {
    fn from(value: LdtkGridTile) -> Self {
        Self {
            flip_x: value.f | 1 == value.f,
            flip_y: value.f | 2 == value.f,
        }
    }
}
```

The data is now available to wanderrust. 

### SPAWNING & RENDERING

`tilemap.rs` needs to change in `generate_tile_bundles()` in order to accommodate the new definition of LevelSpec. The list of `TileSpec` should drive the creation of `TileBundle` directly, as presently there's an unnecessary layer of indirection.

```rust
#[derive(Bundle, Clone)]
pub struct TileBundle {
    pub map_tile: MapTile,
    pub tile_idx: TileIdx,
    pub cell: Cell,
    pub tile_xform: TileXform, // new
    pub transform: Transform,
    pub sprite: Sprite,
    pub revealed: Revealed,
    pub child_of: ChildOf,
    pub vis: Visibility,
}
```

Finally, `sync_tiles()` needs to actually query for the xform and update the tiles:

```rust
        sprite.flip_x = tile_xform.flip_x;
        sprite.flip_y = tile_xform.flip_y;
```

## ALTERNATIVES CONSIDERED

### Alternative: GODOT'S TileSetAtlasSource BITWISE OPS 

In Godot, a TileMapLayer uses a TileSet uses a TileSetSource, of which TileSetAtlasSource is one type. TileSetAtlasSource tells the Godot engine how to use an atlas for a given TileSet. The TileMapLayer APIs define a tile with a triple of:

- source ID (i.e. which image to use among those registered as a TileSetSource)
- atlas coordinates (i.e. the X/Y integer coordinates for the tile in the source)
- alternative ID (see next paragraph)

The alternative ID is the key concept here. 

In Godot, The user can create alternative configurations for tiles to change their properties, including simple changes like `flip_v` or `flip_h` or `transpose`, or more complex changes like shaders, custom data on a per-tile basis (i.e. a wall tile with `solid = true` and a "false wall" alternative with `solid = false`). An alternative tile is, from a data model perspective, a tile entirely distinct.

For the purpose of bit-flips like `flip_v` or `flip_h`, the workflow for creating an alternative tile *just* for that operation is cumbersome, so there's a more streamlined approach that encodes a few of these bit flips in the higher order bits on the alternative ID. In this way we can have an `alternative_id` of `0` (i.e. the original tile) *and* we can set/get the flip status using bitwise operators as needed.

A snippet from [`TileSetAtlasSource`](https://docs.godotengine.org/en/stable/classes/class_tilesetatlassource.html#constants) is worth a thousand words:

```gdscript
var alternate_id = $TileMapLayer.get_cell_alternative_tile(Vector2i(2, 2))
if not alternate_id & TileSetAtlasSource.TRANSFORM_FLIP_H:
	# If tile is not already flipped, flip it.
	$TileMapLayer.set_cell(Vector2i(2, 2), source_id, atlas_coords, alternate_id | TileSetAtlasSource.TRANSFORM_FLIP_H)
```

`source_id` and `atlas_coords` are sufficient to identify which tile in which atlas, so `alternative_id` can simultaneously point to one tile unambiguously *and* indicate that the user intends for the tile to be flipped vertically or horizontally.

#### WHY NOT?

We don't do this because we don't have an `alternative_id` system, nor a design for one. 

The very heart of the `tiles!` macro is `enum TileIdx { ( $tile = $idx, )* }` alongside `From<TileIdx> for usize`. This simplicity has paid off again and again; there are zero surprises. The juice is not the worth the squeeze when we have simpler and more straightforward alternatives.

## Alternative: `Option<TileXform>` IN `TileBundle` AND/OR `sync_tiles()`

It *would* be possible to change `tile_xform` to `Option<TileXform>` in both `sync_tiles()` and in `TileBundle`. This would allow `TileIdx` entities without `TileXform`.

Even if the procedures after `ldtk_loader.rs` would treat it as optional, once `TileXform` is a part of that pipeline it's better to keep it. The signature for `TileSpec` is very easy to use and destructure, and as it's part of the loading process, its impact on the rest of the engine would be minimal.

`generate_tile_bundles()` on the other hand could check and supply `Some(tile_xform)` or `None` if `TileXform` is equivalent to `TileXform::default()`. 

On the rendering side, we might paraphrase the query in `sync_tiles()` as `Query<&TileIdx, Option<TileXform>>`. During iteration, `tile_xform_opt.unwrap_or_default()` keeps logic flat and straightforward irrespective of whether the component is present.

#### WHY NOT?

The reason we *don't* do this is two parts: simplicity and consistency. 

Adding another relatively simple Component to every single Tile, especially one that could easily be `#[component(immutable)]`, is simpler and more consistent with Bevy best practices. It means all tiles share the same archetype. 

One potential advantage to omitting this one tiny struct would mean that we could tell immediately whether or not a tile has been flipped: a SystemParam like this `Populated<&TileXform, Changed<TileXform>>` could flip only tiles that need it.

However, this would imply another mutable dereference of `Sprite`, which has effects on [system ordering](https://docs.rs/bevy/latest/bevy/ecs/system/index.html#system-ordering): 

>   By default, the execution of systems is parallel and not deterministic. Not all systems can run together: if a system mutably accesses data, no other system that reads or writes that data can be run at the same time. These systems are said to be incompatible.

If we need to make changes, it's best to do in as few places as possible. `map.rs` handles most generic `Sprite` mutations on its own. 

Systems outside `map.rs` typically select a different a subset of entites with `Sprite`, and they use `ArchetypeFilter`. [This is not true of `Changed<T>` and others](https://docs.rs/bevy/latest/bevy/ecs/prelude/struct.Changed.html#time-complexity):

>   Changed is not ArchetypeFilter, which practically means that if query (with T component filter) matches million entities, `Changed<T>` filter will iterate over all of them even if none of them were changed.

Another way to put it is that `Changed<T>` doesn't operate over components; it operates over entities. The counterfactual is `ArchetypeFilter`. Other wanderrust systems that mutably dereference `Sprite` use an `ArchetypeFilter` like `With<T>` or `Without<T>`. 

Concretely a system that operates on `Query<&mut Sprite, With<MapTile>>` can run in parallel with `Query<Sprite, Without<MapTile>>`, or even `&mut Sprite`, because they rely on archetypes which are clearly disjoint.
